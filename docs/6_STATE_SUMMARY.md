- **T02:** Added a pg pool factory with TLS for Azure PostgreSQL, a withTx helper, and an advisory-locked idempotent SQL migrator. The 001_init.sql schema implements every table from 3_SCHEMAS.md, and tests run against real Postgres.

- **T05:** Added a generic SimpleRepo + crudRoutes factory (whitelisted columns, escaped ILIKE search) and a ProductsRepo that computes totalQuantity across warehouses. Products support normalised SKUs, JSON custom attributes, search/category/low-stock filters, and duplicate-SKU 409s.
- **T06:** Added warehouse CRUD on the generic crud router with uppercase unique location codes. Stock is tracked per product per warehouse from here on.
- **T07:** Added StockService with receive/issue/adjust/transfer. All writes go through one conditional UPDATE (never below zero) plus an immutable ledger row, with row locks taken in a consistent order to avoid deadlocks. A 25-way race test proves no overselling, and post-commit observers enable realtime and alerts.
- **T08:** Added supplier and customer CRUD with email/phone validation. CustomersRepo.findOrCreateByChannel idempotently maps a chat identity (e.g. a WhatsApp number) to a customer record.
- **T09:** Added SettingsService (JSONB key/value merged over defaults) for business name, currency, WhatsApp number, default warehouse, alert recipients and custom field definitions. Admins change them via PUT /api/settings without redeploying.
- **T10:** Added an in-process EventBus and an authenticated /api/events Server-Sent Events stream with heartbeats and a connection cap. Stock changes now publish stock.changed events carrying the new warehouse and total quantities.
- **T11:** Added OrdersService: create (price snapshot, merged lines), confirm (all-or-nothing stock deduction from the chosen or default warehouse), fulfill, and cancel (restocks confirmed orders). Every transition publishes realtime events and calls status observers, which customer notifications will use.
- **T12:** Added /api/dashboard KPIs (active products, units, stock value, low-stock count, pending orders, orders today) in one SQL round trip. AlertService fires a stock.low event and chat alerts to the configured recipients only when a product's total crosses down through its reorder level.
- **T13:** Added channel adapters for the WhatsApp Cloud API, Messenger/Instagram Page Send API and Telegram Bot API, with 10s timeouts and errors that never include tokens. ChannelHub routes, skips unconfigured channels, and logs every outbound message, and MessagesRepo de-duplicates inbound webhook retries by external id.
- **T14:** Added BotService for help/catalog/stock/price/order/status across every channel, with currency formatting from settings and status lookups limited to the customer's own orders. InboxService de-duplicates, logs, publishes message.received and sends the bot reply.
- **T15:** Added /webhooks/meta (verify-token handshake plus timing-safe X-Hub-Signature-256 HMAC over the raw body) and /webhooks/telegram (secret-token header). Payloads are parsed with permissive zod schemas, echoes and non-text messages are skipped, and webhooks fail closed (503) when secrets are unset.

Added the anonymous /api/public/catalog (safe fields only) and a rate-limited /api/public/orders that checks availability and creates web customers and orders.

## Log
- **T89** Tenant context, app DB role and row-level security (2026-11-26): Added row-level security: a tenant context (AsyncLocalStorage) and a pool wrapper that switches every connection to the restricted role stocksync_app and binds it to the current tenant (fail closed, callback-style access refused), migration 011 with a policy on every tenant table, and a startup check that refuses to serve unless the role is restricted. Tests prove raw SELECT/UPDATE/DELETE with no WHERE touch only the current tenant, cross-tenant writes are rejected, no context means no data, a tenant never leaks across reused connections or 50 interleaved requests, and a guard fails if any future table skips RLS. The whole existing suite (453 tests) and the browser e2e pass under the restricted role. Decision D-018a: policies are ENABLEd rather than FORCEd (FORCE would blind future owner-run data migrations), compensated by the fail-closed role switch and the startup assertion; the default tenant now has a fixed id.
- **T90** Tenant-scoped numbering, settings and counters (2026-11-26): Proved and completed per-business numbering: two tenants run the real services side by side with identical SKUs, barcodes and warehouse codes, orders, purchase orders and counts each start at 1, invoices both issue INV/2026-27/000001 and 15 interleaved confirmations per tenant give each its own gapless sequence, settings and webhook event ids are independent, and the same barcode finds each business's own product. Added migration 012 (maintenance_runs per tenant with RLS) and a test helper to add tenants.
- **T91** Users, login and platform admins per tenant (2026-11-26): Users now belong to one business: login finds the business from the email through a narrow SECURITY DEFINER lookup, tokens carry a type and a tenant id, and every request runs inside that tenant (a user id from another business with this tenant's claim, old-style tokens, wrong-type tokens and other secrets are all refused). Suspended businesses cannot log in and their existing tokens stop working, without revealing suspension to a wrong password. Platform staff have their own table, token key, login and database role that has no grants on any business table; a business cannot read them or change its own status or plan with raw SQL. The console can list businesses and suspend or reinstate them.
- **T92** Tenant-aware jobs, maintenance, realtime and ops (2026-11-26): Background work is now business-aware: jobs record the business that enqueued them and run inside its tenant context whichever worker picks them up, the dedupe key is per business, outbox jobs carry the sender's business, and the scheduler works through every active business separately (each with its own settings and maintenance records). Live events are tagged with their business and SSE streams are scoped to the subscriber's business (an event with no context goes only to the single-business fallback). /api/ops/status shows only the caller's own queue and failures, and a platform-only /api/platform/queue shows whole-platform queue health and worker heartbeats. Decision: the job table is deliberately not row-level secured (workers claim across businesses; it holds ids and kinds only), recorded as an exemption in the guard test.
- **T93** Per-tenant public shop (2026-11-26): Every business now has its own public shop: /shop/<slug> with /api/public/s/<slug>/catalog and /orders, its own cart storage per business, its own installable-app manifest (name and start page), and unknown, malformed or suspended slugs are plain 404s. Shopper order and invoice links are unguessable tokens that find their business by themselves through narrow SECURITY DEFINER lookups (ACTIVE businesses only; the signed invoice link is verified before any lookup), and the order page links back to the right shop. The original /shop and /api/public/catalog URLs keep serving the default business (served directly rather than redirected, which is equivalent while one business exists).
- **T94** Per-tenant channel credentials and webhook routing (2026-11-26): Each business now keeps its own channel and payment credentials: AES-256-GCM encryption with the business id as associated data (a ciphertext planted in another business cannot be read, tampering and key rotation are tested), a write-only admin API and a Settings card that shows only set/not-set and the last four characters plus the business's own webhook URLs. Sending and online payments resolve the CURRENT business's keys at call time (a business without keys sends nothing and takes no payments; the server's environment keys serve only the default business). Webhooks moved to per-business URLs (/webhooks/meta|telegram|razorpay/<id>) verified with that business's own secret (Meta handshake, signatures, Telegram secret, Razorpay events); unknown, malformed and suspended ids are 404, and the original URLs still serve the default business.
