# 6. State Summary (Rolling Memory)

- **Prompt 1 (Architecture):** Scaffolded the StockSync inventory platform docs (PRD, architecture, schemas, 23-task graph) and `.env.example`. Stack: Node 22/TS, Express 5, PostgreSQL, React/Vite PWA, Meta + Telegram messaging, deployed on Azure Container Apps.
- **T01:** Set up npm workspaces with strict TypeScript 6, ESLint (no-explicit-any enforced) and Vitest. Added a zod-validated env loader that rejects weak JWT secrets and bad DB URLs.
- **T02:** Added a pg pool factory with TLS for Azure PostgreSQL, a withTx helper, and an advisory-locked idempotent SQL migrator. The 001_init.sql schema implements every table from 3_SCHEMAS.md, and tests run against real Postgres.
- **T03:** Added createApp with helmet CSP, CORS allowlist, rate limiting, raw-body capture for webhook signatures, and /healthz. A central error handler maps domain, zod and Postgres errors to safe JSON responses without leaking internals.
- **T04:** Added bcrypt + HS256 JWT login with timing-safe unknown-email handling, per-request user revalidation (deleted users lose access), and a viewer<staff<admin RBAC middleware. Admins manage users via /api/users, and a bootstrap admin is created from env on first start.
- **T05:** Added a generic SimpleRepo + crudRoutes factory (whitelisted columns, escaped ILIKE search) and a ProductsRepo that computes totalQuantity across warehouses. Products support normalised SKUs, JSON custom attributes, search/category/low-stock filters, and duplicate-SKU 409s.
- **T06:** Added warehouse CRUD on the generic crud router with uppercase unique location codes. Stock is tracked per product per warehouse from here on.
- **T07:** Added StockService with receive/issue/adjust/transfer. All writes go through one conditional UPDATE (never below zero) plus an immutable ledger row, with row locks taken in a consistent order to avoid deadlocks. A 25-way race test proves no overselling, and post-commit observers enable realtime and alerts.
- **T08:** Added supplier and customer CRUD with email/phone validation. CustomersRepo.findOrCreateByChannel idempotently maps a chat identity (e.g. a WhatsApp number) to a customer record.
- **T09:** Added SettingsService (JSONB key/value merged over defaults) for business name, currency, WhatsApp number, default warehouse, alert recipients and custom field definitions. Admins change them via PUT /api/settings without redeploying.
- **T10:** Added an in-process EventBus and an authenticated /api/events Server-Sent Events stream with heartbeats and a connection cap. Stock changes now publish stock.changed events carrying the new warehouse and total quantities.
- **T11:** Added OrdersService: create (price snapshot, merged lines), confirm (all-or-nothing stock deduction from the chosen or default warehouse), fulfill, and cancel (restocks confirmed orders). Every transition publishes realtime events and calls status observers, which customer notifications will use.
- **T12:** Added /api/dashboard KPIs (active products, units, stock value, low-stock count, pending orders, orders today) in one SQL round trip. AlertService fires a stock.low event and chat alerts to the configured recipients only when a product's total crosses down through its reorder level.
- **T13:** Added channel adapters for the WhatsApp Cloud API, Messenger/Instagram Page Send API and Telegram Bot API, with 10s timeouts and errors that never include tokens. ChannelHub routes, skips unconfigured channels, and logs every outbound message, and MessagesRepo de-duplicates inbound webhook retries by external id.
- **T14:** Added BotService for help/catalog/stock/price/order/status across every channel, with currency formatting from settings and status lookups limited to the customer's own orders. InboxService de-duplicates, logs, publishes message.received and sends the bot reply.
- **T15:** Added /webhooks/meta (verify-token handshake plus timing-safe X-Hub-Signature-256 HMAC over the raw body) and /webhooks/telegram (secret-token header). Payloads are parsed with permissive zod schemas, echoes and non-text messages are skipped, and webhooks fail closed (503) when secrets are unset.
- **T16:** OrderNotifier now messages chat customers on their own channel when an order is confirmed, fulfilled or cancelled. Added /api/channels (configuration status), /api/messages (inbox log) and /api/messages/send for staff replies, with provider failures returned as 502.
- **T17:** Added ImageStorage, which issues 10-minute write-only Azure Blob SAS URLs for png/jpeg/webp/gif so browsers upload directly to Blob. Added the anonymous /api/public/catalog (safe fields only) and a rate-limited /api/public/orders that checks availability and creates web customers and orders.
- **T18:** Added index.ts, which validates env, runs migrations, bootstraps the admin, ensures the Blob container, enables Application Insights when configured, and shuts down gracefully on SIGTERM. createApp now serves the built SPA with immutable asset caching and an index.html fallback, and a smoke test of the compiled server passed.
- **T19:** Scaffolded the React 19 + Vite + React Router web app with a typed API client (types imported straight from the API domain contracts), an auth context with role checks, an SSE client that sends the JWT in a header, and a responsive sidebar layout with light/dark themes. Login is covered by Testing Library tests.
- **T20:** Built the Dashboard (KPIs, reorder list, pending orders, live SSE feed that auto-refreshes the numbers) and Products (search/filter, categories, a form with dynamic custom fields from Settings, and direct-to-Azure-Blob image upload via SAS). Added /api/uploads/status so the UI only offers uploads when Blob Storage is configured.
- **T21:** Built Inventory (receive/issue/adjust/transfer form plus filterable stock levels), the Movements ledger view, and a generic CrudPage now used for Warehouses (and later Suppliers/Customers). Fixed blank optional fields being sent as null and mapped Postgres not-null violations to 400.
- **T22:** Built Orders (status tabs, confirm from a chosen warehouse, fulfil/cancel, manual order creation), the omnichannel Inbox (conversations grouped per channel user, live refresh, staff replies), Customers/Suppliers, and admin-only Settings (business info, alert recipients, custom product field editor, channel status) and Users.
- **T23:** Built the public /shop storefront (search, availability-capped cart persisted locally, web checkout, and an 'Order on WhatsApp' deep link that pre-fills bot order commands, which the bot now merges into one multi-item order). Added a PWA manifest, PNG/SVG icons and a service worker that never caches /api, and verified the app end to end in Chromium with zero console errors.
- **Prompt 4 (Security audit):** Static scans, dependency audits and a controls review passed. Patched dev-only minimatch, added request logging, made chat data staff-only, and added self-service password change (see 7_SECURITY_AUDIT.md).
- **Prompt 5 (DevOps):** Added a multi-stage non-root Dockerfile, a docker-compose stack (app + PostgreSQL + Azurite, verified healthy with a real browser image upload), Bicep for the full Azure topology (compiles with zero lint warnings), a GitHub Actions CI/CD pipeline using OIDC, and DEPLOYMENT_GUIDE.md.

- **T37** Payment messages in chat and staff payment-link endpoint (2026-11-06): Chat checkout now offers Pay online when Razorpay is configured, creates an ONLINE order and replies with a Pay URL button; paylink:<n> safely resends links for the customer's own unpaid online orders, and provider outages leave the order in place with a Try again button. A verified payment sends the customer one 'payment received · confirmed' message (refund notice if it can't be fulfilled), and staff get POST /api/orders/:id/payment-link with optional delivery to the customer's chat, with provider errors mapped to a safe 502.
- **T47** Fix: cancelling a PAID order never flags the refund (2026-11-06): Cancelling an order that was already paid now flags it REFUND_DUE (decided on the database row, so a concurrent webhook can't be missed), publishes payment.updated and alerts staff to refund in Razorpay; the customer gets a single cancellation message that mentions the refund. Unpaid and cash-on-delivery cancels are unchanged.
- **T48** Fix: cancelling an order leaves its payment link payable (2026-11-06): Cancelling an order now marks its open payment link CANCELLED locally and cancels it at Razorpay on a best-effort basis, so an outage cannot block a cancellation. If the customer still pays the stale link, the webhook recognises it as paid-after-cancel and flags REFUND_DUE with staff and customer notices (tested).
- **T49** Fix: a second payment for an already-paid order is not flagged (2026-11-06): When a different payment link of an already-paid order is paid, the extra payment is now recorded, staff are alerted with the order number and pay_ id to refund the duplicate, and the customer is told; the order stays PAID and confirmed and stock is deducted once. Re-deliveries under new event ids don't re-alert.
- **T50** Fix: paid order without a default warehouse is wrongly marked REFUND_DUE (2026-11-06): A paid order that can't be auto-confirmed only because no default warehouse is configured now stays PENDING and PAID: staff are told to set a default warehouse and confirm by hand, and the customer is told payment was received (no refund wording). Only genuine failures such as insufficient stock still become REFUND_DUE.
- **T51** Fix: Razorpay HTTP call runs inside a held DB transaction (2026-11-06): linkForOrder no longer holds a pooled DB connection while waiting on Razorpay: it reuses an open link, calls Razorpay with no transaction open, then persists under a short per-order lock that re-checks the order (cancelled or already paid becomes a 409 and the fresh link is cancelled) and any racing request (the loser's link is cancelled). With Razorpay 2 s slow and 15 requests in flight against a pool of 10, /healthz now answers in under a second.
- **T38** Public checkout API with payment methods (2026-11-06): POST /api/public/orders now accepts paymentMethod (defaulting to the first enabled method, rejecting disabled ones with 409), returns an unguessable tracking token and, for ONLINE, a Razorpay paymentUrl whose amount always comes from the server; if the provider is down the web order is cancelled so no orphans remain (502). New GET /api/public/orders/:token returns only safe fields (no personal data or internal ids, no-store) with the pay URL while payment is pending, and the catalog lists the usable paymentMethods.
- **T39** Shop payment choice, redirect and order status page (2026-11-06): The shop checkout now offers the enabled payment methods (pay online first, a single method shown as text, none disables ordering); an accepted order empties the cart, ONLINE sends the shopper to the Razorpay page and COD goes to the new /shop/order/:token status page, while an unsafe payment URL is never followed.
