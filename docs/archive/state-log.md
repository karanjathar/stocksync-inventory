# Archived state log
Older entries moved here by `engine compact`. Read only when you need history.

- **T24** BotReply model, normaliser and plain-text fallback (2026-11-06): Added the channel-neutral BotReply model with normaliseReply (clamps to WhatsApp limits and 64-byte action ids, never throws), renderPlain numbered-text fallback, and numbered-choice resolution. Interactive text is capped at 1024 chars, plain text at 4096.
- **T25** WhatsApp interactive rendering (buttons, list, cta_url) (2026-11-06): WhatsAppAdapter.sendReply renders normalised BotReplies as Cloud API interactive button, list and cta_url messages, falling back to text when there are no options. ChannelAdapter gained an optional sendReply so adapters without rich UI fall back to numbered text.
- **T26** Telegram inline keyboards and Messenger/Instagram quick replies (2026-11-06): Telegram renders BotReply options as inline keyboards (callback_data = action id, url buttons for links) and gained answerCallbackQuery; Messenger/Instagram render options as quick replies (≤13, titles ≤20) with full list details and links in the message body. Fixed a bug where Messenger showed truncated product names in the body.
- **T27** Parse inbound taps into InboundMessage.action (2026-11-06): Inbound parsing now maps WhatsApp button_reply/list_reply/template buttons, Messenger/Instagram quick replies and postbacks, and Telegram callback_query to InboundMessage.action, and the Telegram webhook answers callback queries. Webhook tests no longer reset the shared test DB mid-file (they build a second app on the same pool); numbered-reply mapping moved to T28 (D-009).
- **T28** Hub, inbox and bot speak BotReply (2026-11-06): The bot now returns BotReply (welcome/help carries a Browse button; tapped actions route to the matching command, typed v1 commands unchanged), ChannelHub.reply renders per channel or as numbered text and logs readable text plus the options shown, and the inbox maps a bare number to the last options (migration 002_reply_options). Kept typed 'menu' as the v1 catalog alias.
- **T44** Fix: truncate() can split emoji surrogate pairs (2026-11-06): truncate() now iterates whole code points and stays within the stricter UTF-16 length, so emoji at a cut boundary are dropped instead of split into lone surrogates that Meta can reject. Covered for buttons, list rows and descriptions.
- **T45** Fix: Telegram taps logged as raw action ids in the Inbox (2026-11-06): Label-less taps (Telegram callback_query) are now logged and published to the dashboard with the title of the option that was shown, falling back to the raw action id. The bot still receives the action itself, so routing is unchanged.
- **T29** Migration 003 and Release 2 types (2026-11-06): Added migration 003 (orders payment_method/payment_status/public_token, payments with one-open-payment-per-order index, webhook_events, chat_carts) and the Release 2 domain types; orders expose the payment fields and accept a paymentMethod. Verified the in-place upgrade of a populated Release 1 database in an isolated schema, and the dashboard feed handles payment.updated.
- **T30** Chat cart repository (2026-11-06): Added ChatCartsRepo: one persisted cart per chat customer with add/set/clear under a row lock, live pricing, quantities capped at available stock, and inactive or deleted products dropped on read (the cleanup is persisted and reported as adjusted). Carts are isolated per customer.
- **T31** Menu and browsing flow (2026-11-06): Added ChatFlow for tap actions: menu buttons, catalog of categories with orderable products (+ All products), category pages of 9 with a More… row, product detail with a stock-capped quantity list, and add-to-cart confirmation with Checkout/Keep shopping/Clear cart; stale or malformed taps get a friendly message. Updated two T28 tests that pinned the interim text catalog to the planned interactive catalog contract.
- **T32** Cart and checkout flow (2026-11-06): Added cart, clear, checkout and pay:cod/pay:online flows: checkout offers only enabled methods through an injectable PaymentOptions port (cash on delivery only until Razorpay is wired in T35/T37), placing an order creates it from the live cart with the chosen paymentMethod and clears the cart. Empty or changed carts are explained, and disabled methods are refused.
- **T33** My orders flow (2026-11-06): Added the My orders flow (sender's last 5 orders with status, total, item count and payment method; order:<n> detail with the same not-found answer for missing and other customers' orders), plus a customerId filter on orders.list. Typed 'hi' or unknown text now shows the Browse / My cart / My orders menu (FR-R2-7); three T28/T45 tests were updated from the interim single-button welcome.
- **T46** Fix: concurrent checkout taps create duplicate orders from one cart (2026-11-06): Checkout now takes the chat cart atomically (DELETE … RETURNING inside a transaction) before creating the order, so concurrent or duplicate taps produce exactly one order and the losers see an empty cart; if order creation fails the items are restored and merged with anything added meanwhile. Found by the Phase 6 review with a reproduced race (2 orders from 1 cart).
- **T34** Razorpay client and signature helpers (2026-11-06): Added RazorpayClient (create/cancel Payment Links with Basic auth, injectable fetch, configurable API base for the E2E fake, zod-checked responses, errors without credentials) plus timing-safe webhook and callback signature verification. New env vars RAZORPAY_KEY_ID/KEY_SECRET/WEBHOOK_SECRET/API_BASE, with dummies added to .env.example.
- **T35** Payment service and payment settings (2026-11-06): Added PaymentService: config() explains online availability (keys configured, enabled in Settings, INR only), and linkForOrder() creates or reuses one Razorpay link per order from the server-side total, under a per-order advisory lock so concurrent requests never create two live links. It replaces expired links, switches COD orders to ONLINE, and refuses paid or cancelled orders; settings gained validated payments options and there is a new GET /api/payments/config.
- **T36** Razorpay webhook with idempotent auto-confirm (2026-11-06): Added POST /webhooks/razorpay: raw-body HMAC verification (401 on forgery, 503 when unconfigured), event-id idempotency that releases the id on failure so Razorpay retries, and settlement under row locks: paid links mark the payment and order PAID then auto-confirm from the default warehouse. Amount mismatches, cancelled orders and unfulfillable stock become REFUND_DUE with a staff alert; the confirm step is resumable, so a crash mid-confirm is recovered by the retry (found while writing the failure-path test).
- **T37** Payment messages in chat and staff payment-link endpoint (2026-11-06): Chat checkout now offers Pay online when Razorpay is configured, creates an ONLINE order and replies with a Pay URL button; paylink:<n> safely resends links for the customer's own unpaid online orders, and provider outages leave the order in place with a Try again button. A verified payment sends the customer one 'payment received · confirmed' message (refund notice if it can't be fulfilled), and staff get POST /api/orders/:id/payment-link with optional delivery to the customer's chat, with provider errors mapped to a safe 502.
- **T47** Fix: cancelling a PAID order never flags the refund (2026-11-06): Cancelling an order that was already paid now flags it REFUND_DUE (decided on the database row, so a concurrent webhook can't be missed), publishes payment.updated and alerts staff to refund in Razorpay; the customer gets a single cancellation message that mentions the refund. Unpaid and cash-on-delivery cancels are unchanged.
- **T48** Fix: cancelling an order leaves its payment link payable (2026-11-06): Cancelling an order now marks its open payment link CANCELLED locally and cancels it at Razorpay on a best-effort basis, so an outage cannot block a cancellation. If the customer still pays the stale link, the webhook recognises it as paid-after-cancel and flags REFUND_DUE with staff and customer notices (tested).
- **T49** Fix: a second payment for an already-paid order is not flagged (2026-11-06): When a different payment link of an already-paid order is paid, the extra payment is now recorded, staff are alerted with the order number and pay_ id to refund the duplicate, and the customer is told; the order stays PAID and confirmed and stock is deducted once. Re-deliveries under new event ids don't re-alert.
- **T50** Fix: paid order without a default warehouse is wrongly marked REFUND_DUE (2026-11-06): A paid order that can't be auto-confirmed only because no default warehouse is configured now stays PENDING and PAID: staff are told to set a default warehouse and confirm by hand, and the customer is told payment was received (no refund wording). Only genuine failures such as insufficient stock still become REFUND_DUE.
- **T51** Fix: Razorpay HTTP call runs inside a held DB transaction (2026-11-06): linkForOrder no longer holds a pooled DB connection while waiting on Razorpay: it reuses an open link, calls Razorpay with no transaction open, then persists under a short per-order lock that re-checks the order (cancelled or already paid becomes a 409 and the fresh link is cancelled) and any racing request (the loser's link is cancelled). With Razorpay 2 s slow and 15 requests in flight against a pool of 10, /healthz now answers in under a second.
- **T38** Public checkout API with payment methods (2026-11-06): POST /api/public/orders now accepts paymentMethod (defaulting to the first enabled method, rejecting disabled ones with 409), returns an unguessable tracking token and, for ONLINE, a Razorpay paymentUrl whose amount always comes from the server; if the provider is down the web order is cancelled so no orphans remain (502). New GET /api/public/orders/:token returns only safe fields (no personal data or internal ids, no-store) with the pay URL while payment is pending, and the catalog lists the usable paymentMethods.
- **T39** Shop payment choice, redirect and order status page (2026-11-06): The shop checkout now offers the enabled payment methods (pay online first, a single method shown as text, none disables ordering); an accepted order empties the cart, ONLINE sends the shopper to the Razorpay page and COD goes to the new /shop/order/:token status page, while an unsafe payment URL is never followed. The status page shows server-derived state with live polling that stops when settled or after two minutes, and treats the redirect query only as wording.
- **T40** Orders and Settings UI for payments (2026-11-06): Orders now show the payment method and status as badges (refund-due rows are highlighted with a 'refund the customer in Razorpay' note), offer Send link (chat orders) and Copy link for unpaid orders while online payment is available, show the URL for manual copying if the clipboard is blocked, and refresh live on payment and order events. Settings gained a Payments card with availability explained, the online/COD switches, link validity (min 15, validated), and the Razorpay webhook URL and events to configure.
- **T41** End-to-end tests with a fake Razorpay (2026-11-06): Added npm run e2e: a Playwright run against the production build, with a local fake Razorpay (documented Payment Links API, signed async webhooks, redirect with callback signature) and a fake Meta Graph API, covering 28 checks across the website pay-online flow, a WhatsApp tap-through-and-pay conversation via signed webhooks, forged-webhook rejection and the staff Orders view. Proven able to fail (sabotaging the paid-event handler made it exit 1); added a META_GRAPH_BASE override, default unchanged, so the bot's outbound messages can be captured.
- **T52** Fix: a web shopper cannot get a fresh payment link once the first one expires or is abandoned (2026-11-06): Web shoppers can now resume payment: POST /api/public/orders/:token/payment-link (rate limited, authenticated only by the unguessable token) returns the open link or creates a fresh one for an unpaid online order, and 409s for COD, paid or cancelled orders; the order page shows Pay now while a link is valid and a 'Get a new payment link' button once it has expired or was abandoned. Found by the Phase 8 review, reproduced first: after expiry a web shopper had no way to pay.
- **T53** Fix: the shop forgets an unpaid online order when the shopper backs out of the payment page (2026-11-06): The shop now remembers the last online order token (before sending the shopper to the payment page) and shows 'Continue payment for order #N' while it is still unpaid; the memory is dropped when the order is paid, cancelled or unknown, kept through temporary server errors, and corrupt storage is ignored. Cash-on-delivery orders are never remembered.
- **T54** Fix: customer phone sent to Razorpay is a guess for web shoppers (2026-11-06): Razorpay now receives customer.contact only for WhatsApp customers, whose wa_id always includes the country code; a web shopper's typed digits (with a guessed '+') are no longer sent, so a wrong prefix cannot break link creation and the shopper just enters their number on Razorpay's page. Web, Telegram and other customers send the name only.
- **T55** Fix: Settings lets an admin leave customers with no usable payment method (2026-11-06): The Payments card in Settings now warns, live as the form changes, when the current choices would leave customers with no usable payment method (online needs the server keys, its switch and an INR shop; cash on delivery needs its switch), and stays quiet otherwise. Found by the Phase 8 review: unticking COD while Razorpay was unconfigured silently stopped all ordering.
- **T42** Security review of payments and interactive flows (2026-11-06): Audited Release 2: clean dependency audit, no new secrets or dangerous sinks, no-referrer/no-store on order pages; added a 16-test security regression suite for amount tampering, replay, forged webhooks/callbacks and IDOR (proven by mutation: breaking the signature, ownership or amount check each fails it); documented 15 findings in 7_SECURITY_AUDIT.md. Two new weaknesses were reproduced and filed (T56 plain-http provider URL, T57 order flooding); the unbounded reflection of typed text in status replies was fixed here.
- **T56** Fix: production accepts a plain-http payment/messaging provider URL (2026-11-06): In production, RAZORPAY_API_BASE and META_GRAPH_BASE must now be https (loopback http is still allowed so the local E2E can use its fakes), otherwise startup fails naming the variable; every offending variable is reported at once, and development/test are unchanged. Closes audit finding R2-14: provider credentials could previously have been sent over plain http.
