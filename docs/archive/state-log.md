# Archived state log
Older entries moved here by `engine compact`. Read only when you need history.

- **T24** BotReply model, normaliser and plain-text fallback (2026-11-06): Added the channel-neutral BotReply model with normaliseReply (clamps to WhatsApp limits and 64-byte action ids, never throws), renderPlain numbered-text fallback, and numbered-choice resolution. Interactive text is capped at 1024 chars, plain text at 4096.
- **T25** WhatsApp interactive rendering (buttons, list, cta_url) (2026-11-06): WhatsAppAdapter.sendReply renders normalised BotReplies as Cloud API interactive button, list and cta_url messages, falling back to text when there are no options. ChannelAdapter gained an optional sendReply so adapters without rich UI fall back to numbered text.
- **T26** Telegram inline keyboards and Messenger/Instagram quick replies (2026-11-06): Telegram renders BotReply options as inline keyboards (callback_data = action id, url buttons for links) and gained answerCallbackQuery; Messenger/Instagram render options as quick replies (≤13, titles ≤20) with full list details and links in the message body. Fixed a bug where Messenger showed truncated product names in the body.
- **T27** Parse inbound taps into InboundMessage.action (2026-11-06): Inbound parsing now maps WhatsApp button_reply/list_reply/template buttons, Messenger/Instagram quick replies and postbacks, and Telegram callback_query to InboundMessage.action, and the Telegram webhook answers callback queries. Webhook tests no longer reset the shared test DB mid-file (they build a second app on the same pool); numbered-reply mapping moved to T28 (D-009).
- **T28** Hub, inbox and bot speak BotReply (2026-11-06): The bot now returns BotReply (welcome/help carries a Browse button; tapped actions route to the matching command, typed v1 commands unchanged), ChannelHub.reply renders per channel or as numbered text and logs readable text plus the options shown, and the inbox maps a bare number to the last options (migration 002_reply_options). Kept typed 'menu' as the v1 catalog alias.
- **T44** Fix: truncate() can split emoji surrogate pairs (2026-11-06): truncate() now iterates whole code points and stays within the stricter UTF-16 length, so emoji at a cut boundary are dropped instead of split into lone surrogates that Meta can reject. Covered for buttons, list rows and descriptions.
- **T45** Fix: Telegram taps logged as raw action ids in the Inbox (2026-11-06): Label-less taps (Telegram callback_query) are now logged and published to the dashboard with the title of the option that was shown, falling back to the raw action id. The bot still receives the action itself, so routing is unchanged.
- **T29** Migration 003 and Release 2 types (2026-11-06): Added migration 003 (orders payment_method/payment_status/public_token, payments with one-open-payment-per-order index, webhook_events, chat_carts) and the Release 2 domain types; orders expose the payment fields and accept a paymentMethod. Verified the in-place upgrade of a populated Release 1 database in an isolated schema, and the dashboard feed handles payment.updated.
- **T30** Chat cart repository (2026-11-06): Added ChatCartsRepo: one persisted cart per chat customer with add/set/clear under a row lock, live pricing, quantities capped at available stock, and inactive or deleted products dropped on read (the cleanup is persisted and reported as adjusted). Carts are isolated per customer.
- **T31** Menu and browsing flow (2026-11-06): Added ChatFlow for tap actions: menu buttons, catalog of categories with orderable products (+ All products), category pages of 9 with a More… row, product detail with a stock-capped quantity list, and add-to-cart confirmation with Checkout/Keep shopping/Clear cart; stale or malformed taps get a friendly message. Updated two T28 tests that pinned the interim text catalog to the planned interactive catalog contract.
- **T32** Cart and checkout flow (2026-11-06): Added cart, clear, checkout and pay:cod/pay:online flows: checkout offers only enabled methods through an injectable PaymentOptions port (cash on delivery only until Razorpay is wired in T35/T37), placing an order creates it from the live cart with the chosen paymentMethod and clears the cart. Empty or changed carts are explained, and disabled methods are refused.
- **T33** My orders flow (2026-11-06): Added the My orders flow (sender's last 5 orders with status, total, item count and payment method; order:<n> detail with the same not-found answer for missing and other customers' orders), plus a customerId filter on orders.list. Typed 'hi' or unknown text now shows the Browse / My cart / My orders menu (FR-R2-7); three T28/T45 tests were updated from the interim single-button welcome.
- **T46** Fix: concurrent checkout taps create duplicate orders from one cart (2026-11-06): Checkout now takes the chat cart atomically (DELETE … RETURNING inside a transaction) before creating the order, so concurrent or duplicate taps produce exactly one order and the losers see an empty cart; if order creation fails the items are restored and merged with anything added meanwhile. Found by the Phase 6 review with a reproduced race (2 orders from 1 cart).
- **T34** Razorpay client and signature helpers (2026-11-06): Added RazorpayClient (create/cancel Payment Links with Basic auth, injectable fetch, configurable API base for the E2E fake, zod-checked responses, errors without credentials) plus timing-safe webhook and callback signature verification. New env vars RAZORPAY_KEY_ID/KEY_SECRET/WEBHOOK_SECRET/API_BASE, with dummies added to .env.example.
- **T35** Payment service and payment settings (2026-11-06): Added PaymentService: config() explains online availability (keys configured, enabled in Settings, INR only), and linkForOrder() creates or reuses one Razorpay link per order from the server-side total, under a per-order advisory lock so concurrent requests never create two live links. It replaces expired links, switches COD orders to ONLINE, and refuses paid or cancelled orders; settings gained validated payments options and there is a new GET /api/payments/config.
- **T36** Razorpay webhook with idempotent auto-confirm (2026-11-06): Added POST /webhooks/razorpay: raw-body HMAC verification (401 on forgery, 503 when unconfigured), event-id idempotency that releases the id on failure so Razorpay retries, and settlement under row locks: paid links mark the payment and order PAID then auto-confirm from the default warehouse. Amount mismatches, cancelled orders and unfulfillable stock become REFUND_DUE with a staff alert; the confirm step is resumable, so a crash mid-confirm is recovered by the retry (found while writing the failure-path test).
